## 1. The defect

Three sites drop the upper bound entirely when the period is open:

| # | Site | Feeds |
|---|---|---|
| 1 | `budget_service.py:61-63` (`_compute_spent`) | budgets page, dashboard Budget Progress tile |
| 2 | `forecast_plan_service.py:271-273` (actuals) | Forecasts plan-vs-actual columns |
| 3 | `budget_rebalance_service.py:341-345` (`_gather_facts`) | Smart Budget Rebalance (AI overspend) |

So the open period's spend runs unbounded forward and swallows every future stub's window. Stubs
exist for any org whose admin has opened Budgets (`budgets/page.tsx:97`, `count=1`) or Forecasts
(`ForecastPlansClient.tsx:290`, `count=3`).

**Site 3's guard is dead on every production path.** `suggest_rebalance:492-497` sources its period
from `get_current_period`, which by construction returns the row with `end_date IS NULL`
(`billing_service.py:76-80`), and passes `period.end_date`. So `if period_end is not None:` at
`:344` has never once been taken — the AI overspend surface is not *sometimes* unbounded, it is
**always** unbounded.

**And there is a fourth path the ticket never mentions.** `update_budget:176-177` and
`transfer_budget:274-275` both read:

```python
period = await get_current_period(db, org_id)
end = period.end_date if period.start_date == budget.period_start else budget.period_end
```

`get_current_period` returns the open row, so **`period.end_date` is unconditionally `None`**.
Ship TBD-240 without touching these and `PUT /api/v1/budgets/{id}` and
`POST /api/v1/budgets/transfer` become the *only* remaining unbounded open-period spend queries in
the codebase — the exact defect this ticket is named for, surviving on two endpoints. See D4.

## 2. The design: two helpers, and a floor

### 2.1 Why two, not one

Both a *pure* derived end and a *floored* one are needed, and conflating them breaks TBD-234.

```python
async def period_effective_end(db, org_id, period) -> date | None:
    """Pure roster-derived end. NO CLOCK. For analysis, markers, and TBD-234's
    anomaly kernel. NEVER written to a row."""

async def period_spend_window_end(db, org_id, period, *, today=None) -> date | None:
    """period_effective_end(), then floored at `today` IFF period.end_date IS NULL.
    The window every SPEND query uses."""
```

TBD-240 **blocks TBD-234**, whose deliverable is a gap/overlap anomaly kernel. If the today-floor
lived inside a single shared helper, TBD-234 would inherit a clock-dependent end and its detector
would paint phantom overlaps between the open row's floored window and the historic stubs on every
lapsed org — verbatim the failure `reference_billing_period_boundary_model.md` exists to prevent,
re-created in a subtler form that the raw-`end_date` discipline at `billing_service.py:210-215`
would no longer catch. Ship both now; TBD-234 consumes the pure one.

`period_effective_end` therefore has **no production caller in this ticket** — it is reachable only
through `period_spend_window_end` and the tests. That is deliberate, and its docstring must say so
in the house idiom already used for `reanchor_period_dependents` (`billing_service.py:10-17`):
consumed by TBD-234, do not prune as dead code.

### 2.2 The rule

```
period_effective_end(period):
    if period.end_date is not None:   return period.end_date          # authoritative, verbatim
    s0 = _next_period_start(after=period.start_date)
    if s0 is None:                    return None                     # true roster tail
    return s0 - 1 day

period_spend_window_end(period, today):
    e = period_effective_end(period)
    if period.end_date is not None:   return e                        # never floor a closed row
    if e is None:                     return None                     # roster tail stays unbounded
    return max(e, today)
```

Three clauses, each load-bearing:

- **`end_date IS NOT NULL` returns verbatim, before any floor.** A closed period's end is settled
  fact. Flooring it would silently re-open reported history — the worst outcome available here.
- **`s0 is None` returns `None`.** This is the roster tail: there is no later period for a
  future-dated settled row to belong to, so bounding it would hide spend for no benefit. It also
  keeps fresh orgs, single-period orgs, and most existing fixtures **byte-identical**.
- **`max(e, today)` on the open interior.** See §2.3.

### 2.3 Why the floor is mandatory

`ensure_future_periods` anchors stubs on `base = current.start_date`, not on today
(`billing_service.py:173`), and its own docstring concedes they are "therefore historic" for a
lapsed org (`:159-166`). So for an org whose open row is months stale, the *derived* end lands in
the **past**.

Combine that with §0.2 and the failure is severe. Open `[2026-04-25, NULL)`, stubs 05-25 / 06-25 /
07-25, today 2026-07-28. Naive derived end = **2026-05-24**. Meanwhile `RecurringGenerationJob` is
creating settled transactions dated in July. Those rows then appear in **no editable view at all**:

- the open period's window ends in May, so they fall outside it;
- the stub `[07-25, 08-24]` that contains them has a non-null `end_date` **and** `start_date <= today`,
  so `budgets/page.tsx:105-115` files it under `past`, `:79-85` makes it non-editable, `:352`
  renders the read-only banner, and `:167-174` strips every mutation.

The org's current spending becomes invisible and unbudgetable, and the overspend guardrail
disappears — replacing an over-count with an under-count that is strictly worse. The floor holds
the line at today.

**Rejected alternatives.** *Fall back to unbounded when the derived end is past* — zero improvement
for lapsed orgs, which are precisely the orgs with the most stubs to swallow, and it makes the rule
discontinuous for no gain `max` doesn't already give. *Use the calendar cycle end* — extends past
today, widens the overlap with historic stubs, and imports a second definition of "now".

**Monotonicity — conditional, and revision 1 stated it far too strongly.**

Where today's window is genuinely `[start, ∞)`, the rule yields `[start, max(e, today)] ⊂
[start, ∞)`, and spend is a sum of non-negative `Transaction.amount` (`schemas/transaction.py`
pins `Field(gt=0)` on every write path) over a strictly narrowed row set. So the **raw sums** move
down on `GET /api/v1/budgets`, `GET /api/v1/forecast-plans/*`, and `current_mo_actual`.

**Three places where it does NOT hold, all found in sign-off round 1:**

1. **Derived figures move the other way by construction.** `remaining = budget.amount - spent`
   (`budget_service.py:69`) moves **up**. `_compute_actuals_batch` sums **income** as well as
   expense (`forecast_plan_service.py:269`), so `variance = actual - planned` (`:331`) moves
   **down** on income rows — a *worse* variance, not a better one.
2. **D4's two endpoints can move UP, and the new value is the correct one.** The narrowing argument
   assumes today's bound is `∞`; on `update_budget:177` / `transfer_budget:275` the `else` branch is
   `budget.period_end`, a stored snapshot that can be **stale-narrow**. Reachable with existing
   production data, because pre-#588 `close_period` revived a stub with a bare
   `existing.end_date = None` and **no** budget re-anchor (`git show 3d58d6f0:…billing_service.py`
   `:429-431`): stub `[07-25, 08-24]` budgeted, revived by a close, then closed later at `09-29`
   leaves the period row ending `09-29` while the budget snapshot still says `08-24`. D4 reads the
   authoritative `09-29` and `spent` **rises by five weeks**. The new value is the **authoritative** one — the window the
   period row itself declares — though on a roster that also carries a later stub, ownership of the
   overlap is the same ambiguity §2.3's residual already records. Correct, but not "down".
3. **The AI rebalance response is not monotone in `current_mo_actual`.**
   `movable = min(total_headroom, total_deficit)` (`budget_rebalance_service.py:163-165`): a
   narrowed window *raises* one category's headroom while lowering another's deficit, so `movable`
   can rise and a category's `suggested_amount` / `delta_amount` with it. An org sitting at
   `total_headroom <= 0` can also cross the short-circuit at `:530-543` and flip from
   `status="empty_no_surplus"` (a refusal) to a full set of suggestions. `uncovered_overspend` does
   move down; `total_suggested` is conserved.

This is why the release note (§6) is scoped to the two read surfaces rather than claiming a global
direction, and why D8's no-flag argument is re-grounded below rather than resting on
monotonicity.

**The residual, recorded rather than hidden.** The floor *bounds* the double count on a lapsed
roster; it does not eliminate it. `[04-25, today]` still overlaps the historic stubs. That
double-count happens today already and unbounded; this shrinks it, and it disappears entirely once
the roster converges — which `BillingCloseJob` now does automatically per #588. An unconverged
roster genuinely has ambiguous ownership of today; the right answer is to keep today visible in the
editable row, not to make it invisible everywhere. **Document this in code with a pointer to
TBD-235 blocker 1, so the next reader does not "fix" it by removing the floor.**

### 2.4 The non-inversion invariant

`s0 > period.start_date` strictly (`billing_service.py:429-431`), so `e = s0 - 1 >= start`, and
`max(e, today) >= e >= start`. The window can never invert. This is not decorative:
`_apply_close_step` may legally leave the open row starting **tomorrow** (close with
`close_date = today`), so `today < period.start_date` is a reachable state and must not produce
`end < start`. **`raise`, do not `assert`** — bare `assert` is stripped under `python -O`, and this
is money math. Raise a **non-user-facing** error (`RuntimeError`), never `ValidationError`: this
branch is unreachable, and mapping it to a 400 would turn an internal invariant violation into a
user-facing error on `GET /api/v1/budgets`.

## 3. Decisions

**D1 — Scope: the three unbounded sites plus the two snapshot readers. The `+1 month - 1 day`
trio is out.** Unanimous. Justification in §7.

**D2 — The floor is `max(derived, today)`.** Unanimous. §2.3.

**D3 — Two helpers, pure and floored.** §2.1. Both must carry, in their docstrings, the
prohibition from the boundary-model reference: **never persist either result to
`BillingPeriod.end_date` or `Budget.period_end`**, and **never** use either in
`ensure_future_periods`' arm-2 intersection predicate (`billing_service.py:235-247`) or
`_apply_close_step`'s straddle predicate (`:572-582`). Both of those depend on raw `end_date`
three-valued logic; substituting a derived end there stops stub creation for **every** org,
silently.

**D4 — `update_budget` and `transfer_budget` are in scope, and this is mandatory.** §1 shows they
are unbounded for the *current* period unconditionally. Replace the expression with a lookup of the
budget's **own** period:

```python
# billing_service.py, beside the other two helpers. db.execute, per D7.
async def _find_period_by_start(db, org_id: int, start: datetime.date) -> BillingPeriod | None:
    """The org's period row at exactly `start`, or None. `scalar_one_or_none` is
    safe: uq_billing_period_org_start makes (org_id, start_date) unique."""
```

```python
period = await billing_service._find_period_by_start(db, org_id, budget.period_start)
end = (await period_spend_window_end(db, org_id, period)
       if period is not None else budget.period_end)                    # stranded → snapshot
```

`transfer_budget`'s stranded fallback is **`source.period_end`**, matching today's
`budget_service.py:275`.

**Residual, downgraded in revision 3:** *if* a stranded budget ever existed (it cannot today —
see above) and its stored `period_end` were `NULL`, the fallback would leave `PUT /budgets/{id}`
unbounded for that row. Recorded for the TBD-235 boundary-move future, not as a live gap. §1's
"the only remaining unbounded open-period spend queries" therefore stands as written.

**Implementation note (N7):** `_find_period_by_start`'s body is byte-identical to
`resolve_period`'s non-`None` branch (`billing_service.py:132-142`), differing only in the no-match
behaviour. Implement `resolve_period` **on top of** it rather than adding a fourth copy of the same
SELECT.

Two constraints, both of which a naive implementation gets wrong:
- **Do not use `resolve_period`** — it raises `ValidationError` when no row matches
  (`billing_service.py:141`), which would turn a PUT on a stranded budget into a 400.
  ⚠ *Corrected in revision 3: revision 2 claimed stranded budgets are reachable today via
  `org_data_service.py:144`. **They are not.** `org_data_service.py:129-131` deletes every Budget
  for the org **fourteen lines before** `:144` deletes the periods, in the same transaction, and
  that is the **only** `delete(BillingPeriod)` in the codebase — no route exposes a period delete.
  Every budget is born at a real period start (`create_budget:127`, `create_budgets_from_forecast:333`,
  `copy_budgets_from_period:404` all anchor on a `resolve_period` result).* Keep the
  `scalar_one_or_none` + snapshot fallback anyway as **defence in depth** against TBD-235's
  boundary move — whose crash window `reanchor_period_dependents`' docstring names at `:301-303` —
  and against direct data surgery. Note a stranded budget is unreachable from the UI regardless,
  since `list_budgets` swallows the error and returns `[]` (`budget_service.py:91-93`).
- **Do not use `get_current_period`** — it auto-creates *and commits* a `BillingPeriod`
  (`:96-120`). Today a plain `PUT /budgets/{id}` on an org with no open row silently writes a
  period row. Resolving by `budget.period_start` removes that side effect for free.

`transfer_budget` needs exactly one lookup: `target` is created at or found by `source.period_start`
(`:226`, `:236`), so source and target always share the window.

**Blast-radius note:** this divergence is API-surface only today. `budgets/page.tsx:233-241` and
`:251-266`, and `BudgetRebalanceModal.tsx:160-161`, all discard the response body and refetch via
`list_budgets`. That is why it has gone unnoticed, and why fixing it is cheap.

**D5 — Do NOT change what gets stored, and do NOT change what gets emitted.** `create_budget:149`,
`create_budgets_from_forecast:374` and `copy_budgets_from_period:433` keep storing the **raw**
`period.end_date`; `_to_response:81` keeps emitting the stored column; `forecast_plan_service`'s
`_build_response` keeps emitting the raw `period.end_date`. Derived ends are for **queries only**.
#588 established the snapshot column's meaning precisely (what the period's end *was* when it
closed, refreshed only by `close_period`'s D5); freezing a clock-dependent value into it would be a
new lie in the same column. *Evidence, corrected in revision 2 — revision 1's grep claim was false.* There are ~10 non-Stripe
`period_end` occurrences in the frontend (`lib/types.ts:238`, `:286`;
`DashboardDataProvider.tsx:191`, `:203`; `dashboard/page.tsx:59`, `:75`;
`AccountMonthEndForecast.tsx:32`; `AIForecastRefineToggle.tsx:61`), but they are **type
declarations, not reads**. `grep -rn "\.period_end" frontend/{app,components,lib}` returns exactly
one live read — `app/recurring/page.tsx:429-430` — and it reads the `/recurring/generate`
response's `period_end`, a different payload. So no client reads `BudgetResponse.period_end` or
`ForecastPlanResponse.period_end`, and D5's conclusion stands. Note `lib/types.ts:238` types
`Budget.period_end` as non-nullable `string` while the API emits `null`; pre-existing type lie,
unused, explicitly not fixed here.

**D6 — `today` is injectable everywhere.** Keyword-only `today: datetime.date | None = None` on
`period_spend_window_end` and on the service entry points that call it, defaulting to
`datetime.date.today()` — the D2 pattern already established by `close_period`. This change
introduces the wall clock into **money computation**, so
`reference_wall_clock_date_bomb_tests` applies directly: tests anchor relative to `date.today()`,
never on literals near the clamp boundary. Unlike TBD-241 no production caller needs threading —
all consumers are request-scoped.

**Thread it into `_gather_facts` too.** `budget_rebalance_service.py:294` reads
`datetime.date.today()` internally for the 3-month split. If only the window end is injected, an
injected `today` governs the window while the real clock governs `three_mo_upper` — two clocks in
one computation, and the resulting test is unstable across midnight.

**The exact threading surface** (both round-2 reviewers asked for this; leaving it unstated would
produce two different signatures):
- **Public entry points gain `*, today: datetime.date | None = None`:** `list_budgets`,
  `create_budget`, `update_budget`, `transfer_budget`, `suggest_rebalance`, and
  `forecast_plan_service`'s public plan getters.
- **`_build_response` gains it too**, because it is where the forecast derivation lives
  (`forecast_plan_service.py:289-298`). Its **eleven** callers (`:367, :391, :632, :708, :796,
  :820, :842, :858, :873, :889, :970`) pass it through from their own entry point; none is a loop.
- **`_gather_facts` gains it**, used for both the window and `three_mo_upper`.
- **`_compute_spent` and `_compute_actuals_batch` do NOT** — they receive a resolved date (§4).

Verified: no non-request caller exists for any entry point, so nothing outside a request needs to
supply it.

**D7 — `db.execute`, never `db.scalar`, for anything selecting `BillingPeriod`. House convention,
NOT a live hazard.** *(Demoted in revision 2. Both architects raised it and both sign-off reviewers
independently showed the hazard is unreachable.)*

The patch is real and class-level — `tests/services/test_billing_service.py:165-180` monkeypatches
`AsyncSession.scalar`, one-shot, keyed on a compiled statement containing both `"billing_periods"`
and `"start_date"`. But all five of its users enter through `close_period`, and **none of the new
helpers is reachable from `close_period` or `_apply_close_step`** — they are consumed only by
`budget_service`, `forecast_plan_service` and `budget_rebalance_service`. A `db.scalar` in them
could not consume that firing. Revision 1's claim that it would "silently disable D4 recovery
coverage" was false.

Keep the convention anyway, for consistency with `_next_period_start` (`:421-425`) and
`_lock_period` (`:452-457`) and so a future caller moved into the close path cannot reintroduce
the hazard. There is exactly **one** new select — `_find_period_by_start`. `period_effective_end` delegates to
`_next_period_start` unchanged and `period_spend_window_end` delegates to `period_effective_end`,
so neither adds a statement; do **not** inline a duplicate `MIN(start_date)` query into them.
*(Revision 2 said "all three new selects", which invited exactly that duplication.)* The
by-inspection check is: **no new `db.scalar(select(BillingPeriod)…)` anywhere in the diff.**

**D8 — No feature flag.** `Feature` is a three-member enum (`feature_gate.py:31-33`), each backed
by an env floor, a `SystemSetting` and a per-org `OrgSetting`; a fourth member means config, admin
UI and a permanent branch that a follow-up must then remove. More importantly, a flag on a
*correctness* fix leaves half the fleet reading a number known to be wrong with no way to tell from
the response which semantics produced it. Note `routers/budgets.py` and `routers/forecast_plans.py`
carry **no** `require_feature` at all — only the AI rebalance is gated (`routers/ai_budget.py:45`,
`ai.budget`), which conveniently means the gated surface cannot be where anyone first notices.

**D9 — The pre-#588 snapshot backfill is DEFERRED, not bundled — and the legacy shape is wider
than revision 1 said.** Architect A ruled no backfill; Architect B proposed a severable alembic
revision. **Ruling: deferred to its own ticket.** D4 removes the *spend* consequence by routing
around the column, which is this ticket's whole remit; the remainder is a cosmetic `period_end` on
a response field no client reads (D5). A migration in a no-migration PR widens the revert unit for
no user-visible gain.

**⚠ Two legacy shapes, not one** (revision 1 named only the first):
1. `period_end IS NULL` — budget created while its period was open, closed before #588's D5
   shipped. Reading the authoritative end makes spend move **down**.
2. `period_end` non-null but **disagreeing** with the period row's `end_date` — produced by the
   pre-#588 revive (`3d58d6f0` `billing_service.py:429-431`, `existing.end_date = None` with no
   budget re-anchor) followed by a later close at a different date. Reading the authoritative end
   can make spend move **up** (§2.3 case 2).

The deferred backfill must cover both, and test 14b below covers the second. A third reason to do
it eventually: post-D4, a shape-2 row emits a self-inconsistent payload — `_to_response:81` still
ships the stored `period_end` (08-24) while `spent` is now computed through 09-29. Harmless under
D5 since no client reads it.

## 4. Query shape

`_compute_spent` runs once per budget row (`budget_service.py:107-113`), so a per-call successor
lookup would be N+1. It is avoidable for free, because **`_compute_spent` does not derive the
window — its callers do.**

**`_compute_spent`'s signature does not change.** It keeps

## 6. Rollout

**Direction is NOT uniformly down** — see §2.3, which revision 1 got wrong. It is down on the two
read surfaces; it can rise on D4's two write-response endpoints and on the AI rebalance.

| Surface | Endpoint | Movement | Gate |
|---|---|---|---|
| Budgets page + dashboard Budget Progress tile | `GET /api/v1/budgets` | `spent` ↓, `remaining` ↑ | none |
| Forecasts plan-vs-actual | `GET /api/v1/forecast-plans/*` | actuals ↓ | none |
| Smart Budget Rebalance | `POST /api/v1/ai/budget/rebalance` | `uncovered_overspend` ↓ and `total_suggested` conserved, but `suggestions[*].suggested_amount` may **↑** and `status` may leave `empty_no_surplus` (§2.3 case 3). *(`current_mo_actual` is internal to `_CategoryFact`, not a response field.)* | `ai.budget` |
| API only, not rendered | `PUT /budgets/{id}`, `POST /budgets/transfer`, `POST /budgets` | **↓ on the ordinary current-open-period case** (§1's fourth path — the dominant one, every inline edit and every rebalance apply); ↓ on legacy shape 1 and on stale-**wide** shape 2; **↑ on stale-narrow shape 2** (D9) | none |

Magnitude by org shape: **healthy** (on-grid, stubs ahead) loses only genuinely future-dated
entries — typically zero rows, since recurring generation never creates them
(`recurring_service.py:309-312` settles only `due <= today`). **Lapsed** loses only rows dated
strictly after today; nothing dated today or earlier moves, which is the entire point of the floor.
**Roster-tail** (fresh orgs, orgs that never opened Budgets/Forecasts) — **zero change**.

D4's readers are where spend moves **most**, in both directions: down on the ordinary
current-open-period case (§1's fourth path, unbounded today) and on stale-wide snapshots, up on
stale-narrow ones (§2.3 case 2). In every case the new value is the **authoritative** one — the
window the period row itself declares. *(Revision 2 said here that it "only ever removes spend that
never belonged to the period", which contradicted both its own rollout table and §2.3 case 2.
Caught in round 2.)*

**Release note**, scoped to the two read surfaces rather than claiming a global direction:
> Budget "spent" and forecast "actual" figures for the open billing period now stop at the day
> before the next period begins, or at today, whichever is later, instead of counting future-dated
> transactions. Those figures can only decrease; "remaining" and "% used" move correspondingly the

*(Revision 1 said "Figures can only decrease" flatly; revision 2 narrowed it to "on those two

## 7. Out of scope

**The `+1 month − 1 day` fallback trio — `forecast_service.py:61`,
`account_balance_forecast_service.py:67`, `forecast_plan_service.py:410`.** Unanimous. Four
grounds:

**⚠ Revision 1 rested this fence on four grounds. Both sign-off reviewers independently disproved
two of them. The fence stands on the surviving two, plus the narrower true half of the first — but
the residual is larger than revision 1 admitted and is now recorded.**

1. **~~These three bound a forward projection horizon, not a spend window.~~ FALSE as stated.**
   Each `p_end` is *also* reused as the upper bound of a backward-looking settled sum:
   `forecast_service.py:76-88` bounds `executed_income` / `executed_expense`
   (`status == SETTLED`, `settled_date <= p_end`) and `:101-113` the pending pair;
   `forecast_plan_service.py:580-581` bounds a `SETTLED`+`PENDING` sum;
   `account_balance_forecast_service.py:86-95` bounds a pending aggregate. Same defect class as the
   in-scope three.
   **The true and surviving half:** each `p_end` *additionally* bounds a forward projection —
   `forecast_service.py:120-126` selects `next_due_date <= p_end AND > today` and `:133-139`
   iterates `while d <= p_end`; `forecast_plan_service.py:470-485` does the same; and
   `account_balance_forecast_service.py:170` and `:240` pass `p_end` as the horizon into
   `cc_forecast_service.synthesize_account_cc_payments` and the loan equivalent. Clamping the
   horizon to a derived-or-today value would **zero the recurring contribution for exactly the
   lapsed orgs §2.3 is about**, gutting the forecast tile. So these sites cannot simply adopt the
   spend window: they would need the two bounds *separated* first, which is a refactor, not a
   predicate swap. **That** is why they are out of scope.
2. **~~They are never unbounded, so they cannot swallow a future stub's window.~~ FALSE — bounded
   is not the same as non-overlapping.** Off-grid open row `[2026-07-10, NULL)` with stub
   `[2026-07-25, 2026-08-24]` gives `p_end = 2026-08-09`, swallowing 07-25 … 08-09 of the stub's
   window — precisely the harm this ticket is named for, on a site left out of scope.
3. **On the common path they are already identical to the derived end.** The first stub start is
   `_snap_to_cycle(base + 1 month, cycle_day)` (`billing_service.py:176`); when the open row sits
   on the cycle day — which `current_cycle_window` produces, though **not** every `close_period`
   chain: a manual UI close sends no date, so `requested = today - 1` and `new_start = today`,
   off-grid unless today happens to be the cycle day (`billing_service.py:774-778`). That is
   precisely how ground 2's off-grid roster arises. With `cycle_day` ∈ [1, 28] so month-length
   clamping never bites, and
   with `cycle_day` constrained to [1, 28] so month-length clamping never bites, `_snap_to_cycle`
   is the identity and the two expressions are **byte-identical**. They diverge only on an off-grid
   roster, which is TBD-235 by name.
4. **Two of them emit `period_end` as a required non-null response field**
   (`schemas/forecast.py:57`, `:87`; `AccountMonthEndForecast.tsx:32`). Changing them means
   deciding what "period end" means for a projection — a separate decision.

Recorded as a follow-up, and it is now a *named defect* rather than a tidy-up: **separate the
settled-sum bound from the projection horizon at all three fallback sites, then adopt
`period_spend_window_end` for the former.** Worth doing; too large for this ticket.

**Accepted residuals, stated plainly because both reviewers caught revision 1 understating them:**

- **Two dashboard tiles will disagree on the same period.** After this fix, on a lapsed or
  off-grid roster, `GET /api/v1/budgets`'s `spent` is summed over `[start, max(e, today)]` while
  `GET /api/v1/forecast`'s `executed_expense` for the *same* open period is summed over
  `[start, start + 1 month − 1 day]`. For the §2.3 roster that is `[04-25, 07-28]` versus
  `[04-25, 05-24]` — months apart, side by side on one screen. This divergence **exists today**
  (unbounded vs fallback) and is *reduced*, not created, by this change; on an on-grid converged
  roster — one whose open row has already been closed onto the current cycle — it is zero, and on
  the cycle-boundary day before convergence it is one day (§6). But it is real and it must not be
  discovered later as a surprise.
- `forecast_plan_service` will hold both shapes in one file — `_build_response` on the derived
  end, `populate_from_sources` on the fallback. A comment must name the two semantics, or a future
  reader will unify them and break the recurring synthesis.

**Also out:** repairing lapsed rosters or re-anchoring `ensure_future_periods` on today (TBD-235
blocker 1); the `closed_at` column (TBD-233); the pre-#588 NULL-snapshot backfill (D9); adding a
`window_end` field to `BudgetResponse` so the UI could say "counting through Aug 24" (good
