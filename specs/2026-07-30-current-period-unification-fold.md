## 1. D1 — `open` shadows `upcoming`. Keep it. Engineering call, not the operator's.

`periodStatus`'s `open` branch precedes `upcoming`, so an open row with a future `start_date` is
`open` only. On `main` it satisfied **both** `isCurrentPeriod` and `isNextPeriod`, i.e. `main`
rendered the `current` pill and the `next` pill on the same row. That is not a state worth
preserving.

**The reported CTA loss was overstated by the review, twice over.** `isEditable` is unchanged
(`budgets/page.tsx:92`, via `isCurrentPeriod`), so `+ Add Budget`, the edit/transfer/delete
apparatus and the header `From Forecast` all survive. Exactly two affordances move, and one of
them — `Copy this period` — sources from `selectCurrentPeriod(periods)`, which on that roster **is
the selected row**: `main` offered a button that copied a period onto itself. Restoring a separate
clock-based `isNextPeriod` would re-ship that self-referential control. The genuine loss is the AI
draft button, replaced by the current-period empty state.

**Reachability:** no UI path creates this roster. Nothing in `frontend/` posts
`POST /billing-period` with dates; the UI close button sends no `close_date`, so
`requested = today - 1` and `new_start <= today`. It is reachable by a hand-crafted admin API call
(`?close_date=<today>`, since `billing_service.py:1022` guards with strict `>`), by `seed.py`, or
by a direct DB edit — **plus one path that touches real users: timezone skew.** The server opens a
row at the server's UTC date; a user west of Greenwich whose local date is still the previous day
sees `start_date > todayISO()` for up to ~12 hours.

**Why this is not a product escalation.** The test is whether a real user can reach the state and
whether the change alters what they can *do*. Capability is unchanged; what changes is one seeding
shortcut in an empty state, transiently, on a period whose copy-forward source is itself.
Escalating it would be manufacturing an escalation and would ask the operator to adjudicate a
roster the anomaly kernel exists to flag as corrupt. **Decided here. Recorded in the PR body.**

## 3. D3 — the hydration hazard the branch introduced

`ForecastPlansClient.tsx:266` replaced `main`'s `new Date().toISOString().slice(0,10)` (UTC,
hydration-stable) with `todayISO()` (`frontend/lib/format.ts:24`, **local**). Its parent
`forecast-plans/page.tsx` is an async Server Component passing real `initialPeriods`, so this is
**the one page that prerenders with data** — `budgets` and `dashboard` load periods in `useEffect`,
`DashboardDataProvider` uses SWR. Production Node runs UTC. The divergent value feeds
`isFuturePeriod`/`isPastPeriod`, rendered at `:913-919` and `:1000-1009`.

The hazard fires on a `no_open` roster, where `selectCurrentPeriodIndex` returns `-1`, index 0 is a
closed/stub row, and the flags become genuinely clock-dependent — not exotic, it is the roster this
ticket keeps invoking.

**Ruling: keep the local clock, defer it to `useEffect`.** Both architects proposed the identical
shape.

```ts
const [today, setToday] = useState<string | null>(null);
useEffect(() => { setToday(todayISO()); }, []);
const _planStatus = selectedPeriod && today ? periodStatus(selectedPeriod, today) : null;
const hasCurrentPeriod = selectCurrentPeriod(periods) !== null;      // clock-free, unchanged
const isCurrentPeriod = selectedPeriod ? isOpenPeriod(selectedPeriod) : false;  // clock-free
```

Server pass and first client pass both render `today === null`, so the trees match **by
construction**, not by suppression. `isCurrentPeriod` must stay clock-free via `isOpenPeriod` —
gating it behind the effect would make the "current" pill and the Today button flash on every
healthy roster. This is not a reintroduced second rule: `end_date === null` implies not-inverted,
so `isOpenPeriod(row) ⟺ periodStatus(row, anyToday) === "open"`.

**Rejected:** reverting to UTC (a UTC clock is wrong for the user for ~13 hours of every day at
UTC+13, silent, permanent, and unfixable from the client — and it produces the same
"Past here, Current there" divergence this ticket exists to remove); `suppressHydrationWarning`
(silences the warning while still committing the server's UTC-derived label to the DOM); passing a
server-computed date as a prop (the server has no knowledge of the user's timezone — it launders
the bug into an unfixable one).

**Symptom at UTC+13, 02:00 local:** first paint shows no pill and the neutral guidance string; one
tick after hydration the correct local-date pill and guidance appear. No console error, no wrong
label ever committed.

Add a comment naming the SSR asymmetry, so a future refactor that RSC-seeds budgets or dashboard
does not silently inherit the hazard.

**F6(d), and why it is a correctness fix rather than tidy-up.** The current partition is
`past = filter(bp.start_date <= today)` / `future = filter(bp.start_date > today)`, then
`pl = [future[0], ...past]`. On the D1 roster it does not merely misfile the open row — with a
genuine closed stub also present, **both** land in `future`, `future[0]` takes the open row, and
**the stub is discarded entirely**, so the user cannot budget next period at all. The adjacent
comment's `[next, current, prev, …]` invariant is false on the same roster D1 rules on.

```ts
const isNext = (bp: BillingPeriod) => periodStatus(bp, today) === "upcoming";
const future = (p ?? []).filter(isNext).sort((a, b) => a.start_date.localeCompare(b.start_date));
const rest   = (p ?? []).filter((bp) => !isNext(bp));
const pl = future.length > 0 ? [future[0], ...rest] : rest;
```

`future` and `rest` are complements over one array, so the partition is **total by construction** —
no row can vanish. (An earlier objection that routing this through the classifier makes the open
row disappear targets a naive `filter(status === "upcoming")` / `filter(status === "past")` pair,
not this.)

This does **not** violate `reference_analysis_domain_vs_display_window` §1. §1 forbids a display
window defining an analysis *domain*; this runs the other way — the classifier decides which row
occupies the "next" slot and the complement takes the rest. The window stays a window and stays
total. The argument for touching it is **not** "everything must route through the predicate" (that
framing is rejected): it is that the file currently decides one question twice, six lines apart —
`isEditable` at `:87-92` is classifier-derived, the partition at `:113-118` is raw-clock-derived,
and after D1 they disagree.

Equivalence on every UI-reachable roster: an upcoming stub has `start_date > today` and is not open
⇒ `isNext` under both rules; the current open row has `start_date <= today` ⇒ old `past`, new
`rest`, same position. **Only the D1 roster's output changes.** Null diff everywhere the UI can go.
